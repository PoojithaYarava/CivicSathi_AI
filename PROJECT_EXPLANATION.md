# CivicSathi AI — Project Explanation

This document explains what the project does, how it is built, and how a request moves through it. It describes the current repository, including its limits.

## 1. What the project is

CivicSathi AI is a local information assistant for people looking for Telangana public services. A person can describe what they need in English, Telugu, or a mix of both. The app searches a small catalogue of government services, schemes, forms, and official sources. When it has a researched checklist for the matching service and situation, it shows the documents to prepare and links back to the source.

Its tagline is **“Government services, made easier to understand.”** CivicSathi is an independent information tool. It does not issue certificates, decide eligibility, submit applications or complaints, accept payments, or track government application status.

## 2. How the project is put together

The project has three main parts:

- **Website:** `src/app/static/index.html` contains the page structure, styling, and browser-side JavaScript. It provides the search form, district selector, result cards, checklists, complaint preparation, personal task list, and optional voice controls.
- **Local web server:** `src/app/server.py` uses Python's built-in HTTP server to serve the website and expose JSON API routes. `src/app/service.py` coordinates the catalogue, language/NLP pipeline, search results, and checklist selection.
- **Data and NLP:** CSV files in `data/processed/` hold the catalogues and checklist records. The code in `src/nlp/` normalizes text, estimates language, classifies intent, extracts known entities, and ranks matching records.

The server reads its local data and model when it starts. There is no database or hosted AI service in the core query path. It listens on the local computer (`127.0.0.1`) for development.

## 3. What happens when someone searches

1. The person types a question or uses optional browser speech recognition. The recognized words appear in the editable query box when the browser provides a transcript.
2. The browser sends the query and optional district to the local API. Common sensitive identifiers are screened, and the request is processed in memory rather than saved as query history.
3. Text preprocessing normalizes Unicode and whitespace while preserving Telugu script. A lightweight heuristic estimates whether the text is English, Telugu, or code-mixed.
4. A scikit-learn model predicts one of 12 intents, such as asking for documents or finding a service. Low-confidence results use a fallback instead of pretending certainty.
5. Dictionary-based entity extraction looks for known service names, departments, districts, and dates. This is not a trained general-purpose named-entity model.
6. A word-level TF-IDF index ranks catalogue entries by lexical similarity. The top records and their source details are returned to the website.
7. The response is assembled from catalogue text and templates. For an applicable checklist, service, scenario, and location rules determine which source-backed rows can be shown. If the project has no checklist for that case, the site directs the person to confirm requirements with the official source.

The answer is not generated by an LLM. Retrieval uses word overlap and TF-IDF rather than embeddings or a vector database.

## 4. Documents and location coverage

The processed catalogues currently contain 23 services, 5 schemes, 6 form/document records, and 28 official-source records. There are 35 checklist rows and a directory of all 33 Telangana districts.

Having all 33 districts in the picker supports location selection; it does not mean the project has researched every service in every district. Checklist coverage is limited to the documented GHMC birth/death cases, Telangana MeeSeva residence certificate cases, and a Suryapet-only caste certificate case. Requirements can change and can depend on the applicant's situation. The official source should be checked before travelling or applying. The project does not invent a checklist when evidence is missing.

## 5. Language and voice

Typed queries can use English, Telugu script, or Telugu-English code-mixing. Language detection is heuristic, and Telugu/code-mixed quality has not been independently evaluated by native speakers.

Voice input uses speech recognition supplied by the browser when available; it is not a local speech model or server API. The Telugu-English option is best effort and may be handled as Telugu by the browser's speech engine. Browser support, permissions, microphone access, and vendor speech services affect whether it works. The transcript should be reviewed before searching. The page also uses browser speech synthesis for optional read-aloud support.

## 6. Privacy and saved information

The local server does not store search history. It rejects common patterns for sensitive identifiers, but pattern checks cannot recognize every possible personal detail. The browser stores personal preparation tasks in `localStorage` only after the user chooses to save them; they remain in that browser profile. Voice audio may leave the device if the browser sends it to its speech service. Avoid entering credentials, OTPs, Aadhaar numbers, phone numbers, or other private details.

## 7. Main files and folders

- `src/app/` — local HTTP server, application service, and website.
- `src/nlp/` — normalization, intent classification, entity matching, retrieval, and pipeline orchestration.
- `src/data_processing/` — dataset construction and validation.
- `src/data_collection/` — utilities for collecting public source candidates for manual review.
- `data/processed/` — catalogues, districts, checklist rows, and query examples used locally.
- `models/nlp/` — local model configuration/metrics and generated model artifacts.
- `tests/` — automated tests for data, NLP, and API behavior.
- `notebooks/` — exploratory data and NLP walkthroughs.

Collection utilities are not an unattended official-data crawler. Candidate information must be reviewed before it is used in the catalogues.

## 8. Run it on your computer

In PowerShell from the repository folder, create and activate a virtual environment and install dependencies if this has not already been done:

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
```

Build local processed data and the intent model, then start the site:

```powershell
python -m src.data_processing.build_datasets
python -m src.nlp.train
python -m src.app.server
```

Open `http://127.0.0.1:8000` in a browser. Stop the server with `Ctrl+C`. If the project environment already exists, use `\.venv\Scripts\python.exe` for the commands.

## 9. How the project was evaluated

Automated tests cover dataset validation, text normalization, intent prediction and fallback, entity matching, retrieval provenance, and API behavior. The recorded test suite has 23 passing tests. The intent classifier's perfect held-out score comes from generated, template-based examples, so it does not establish accuracy on real citizens' queries. Retrieval has only a small set of manually written English checks. There is no automated browser or microphone quality evaluation.

## 10. What would be needed before public deployment

The current project is a development MVP, not a production service. A public release would need broader official-source research and freshness checks, native-speaker and citizen testing, browser/accessibility testing, a deployment and security review, and an explicit privacy plan for hosting and voice services. It would also need clear operational ownership for keeping government requirements current.
